# Altitude (SF3500) - dev notes

## Build and test in one place

```sh
SF3500_TC=/path/to/toolchain/host ./build_sf3500.sh     # runtime, compiler, bytecode, fonts (about a minute)
./package.sh                                            # package/ for the card
tools/render-launcher.sh                                # every launcher screen as a PNG, no device needed
tools/bot-run.sh hard 1 100                             # one headless 2P Battle run with the computer opponent
```

Reproducibility: `tools/relpath-cc.sh` (a compiler launcher) passes source files by relative path so the paths
the runtime embeds do not depend on the checkout location (the toolchain's GCC 6.3 has no `-ffile-prefix-map`);
the version banners carry no build date; and `bgdc` honours `SOURCE_DATE_EPOCH` for the date it stores in the
bytecode (the build script sets a constant). Building from two differently named checkouts gives identical files.

`QEMU="flatpak-spawn --host qemu-mipsel-static"` lets the scripts run mipsel programs from inside a
sandbox that has no qemu. Test runs are deterministic: the same build gives the same frame counts and
scores, so a change that should not alter behaviour can be checked by comparing results.

## What differs from the stock runtime

The runtime is BennuGD (SDL2 flavour) with these changes. Everything is under `runtime/`.

* **Display** (`src/sf3500/hwdisp.c`, hooked in `modules/librender/g_screen.c`): the frame is handed to the
  device's display driver instead of SDL. 16-bit frames go straight through; other depths are converted.
  `SF3500_ASPECT=16:9` pads a frame with black bars to that shape. The driver drops frames wider than
  640 pixels, so padding is skipped if the result would be wider.
* **8-bit mode** (`modules/libvideo/g_video.c`): this renderer has no palette path; `set_mode(w,h,8)` left the
  texture format unset and crashed. An 8-bit request now runs on the 16-bit pipeline, which blits 8-bit
  graphics through their palette.
* **Audio** (`src/sf3500/hwaudio.c`, `modules/mod_sound/mod_sound.c`): SDL_mixer's already-mixed output is
  tapped with `Mix_SetPostMix()` and written to the device's audio ring. SDL's own audio device is the dummy
  one. `libsdlhandler` releases the audio hardware on every normal exit as well as on the Select + Start path,
  because the launcher and the game are separate processes started one after the other.
* **Input** (`src/sf3500/joykey.c` and `runtime/sf3500/sdl2-2.0.14-sf3500.patch`): the gamepad is read from
  the shared memory the front-end fills, and turned into SDL keyboard state. Select + Start quits.
  `SF3500_PADMAP=altitude` adds A = Up + Enter, B = Right, Y = Down; `launcher` makes A = Enter, B = Escape.
* **Tracker music**: the game's two songs are `.mod` files. SDL2_mixer is built with libxmp-lite for them
  (`runtime/sf3500/sdl2-mixer-2.6.3-xmp-lite.patch`). libmodplug was tried first and faulted on an
  unaligned access in its loader.
* **Test hooks** (cost nothing unless their variable is set): `SF3500_KEYSCRIPT="60:R,100:E,..."` presses
  keys at frame numbers; `SF3500_SHOT_PREFIX=p` writes the next presented frame to `p_NNN.ppm` whenever a file
  `p.trigger` exists; the computer opponent has `SF3500_BOT_DEBUG`, `_VALIDATE`, `_TRACE` and friends.

Engine facts worth knowing:

* The executable's name must start with `bgdi`, otherwise the engine looks for the game appended to the
  executable instead of reading the file named on the command line.
* The engine reads `VIDEO_WIDTH` and `VIDEO_HEIGHT` at start-up. A script's `set_mode` to a different size
  re-initialises the whole display path, so `run.sh` starts the launcher at its final size.
* `get_screen()` followed by `png_save()` crashes when nothing animates; the frame dump above replaces it.
* `bgdc`'s exit status is not reliable (non-zero after a good compile). The build checks its message.
* The compiler is built from the same tree as the runtime, so the bytecode version always matches.

## The launcher

`launcher/launcher.prg` is an ordinary BennuGD program: it loads the game's own graphics and menu song,
draws four screens, and hands over through two small files: `options.cfg` (settings, written with CRLF line
endings by the engine's `fputs`) and `launcher_action.txt` (`play`, or absent to leave). `run.sh` loops
launcher, game, launcher; anything other than `play` leaves for the front-end.

* It renders at 480x360 on a 640x480 design grid (the leaf drawing functions scale by 3/4). 480x360 padded
  to 16:9 is 640x360, within the driver's frame limit. The panel then scales it up about 1.33x.
* Text uses `.fnt` files generated by `launcher/make-fonts.py` from DejaVu Sans (Condensed) Bold. Glyphs are
  antialiased and pre-blended against the panel colour, so no alpha is needed, and the transparent pixels are
  the engine's colour key (0). The panels must stay opaque and the same colour as `PANEL` in the script.
  `launcher/check-text.py` measures every `label(...)` line with the same fonts and fails the build if one
  would overflow.
* The engine's built-in 8x8 font on translucent panels was nearly illegible on the device; that is why this
  exists.

## The computer opponent (`runtime/modules/mod_grproc/sf3500_bot.inc`)

Player 2 in the script reads only the Z, X and Alt keys and a few globals, so a runtime-side bot can fly it
without touching the game. The input hook calls `sf3500_bot_tick()` every frame and injects the keys it
returns. It acts only if a `Player2` process exists, so it is inert in Arcade and Training.

How it plays:

1. Finds the ship, hazards (ground strips, `Obstacle1-10`, fire pillars) and crystals by process name, and
   reads the game's variables by name from the bytecode's tables (offsets are looked up, not hard-coded).
2. Predicts motion: velocity from the previous frame; the objects that bob up and down (`Obstacle5`,
   `Obstacle8`, all crystals) are replayed exactly from their private `Range`, `VerticalMove`, `TopRange`
   and `MinRange`; rotating objects use their angle and rotation per frame.
3. **Foresight for fire pillars**: a floor cannon (`Obstacle4`) or ceiling cannon (`Obstacle6`) launches a
   pillar when its x passes 327 and again at 177, so the bot adds predicted "ghost" pillars with the
   script's own numbers (start height 315 or -75, 5 pixels a frame, scrolling with the cannon). The second
   pillar is therefore seen more than 50 frames before it exists.
4. Simulates about a second ahead with the game's own flight rules (`bot_flight` copies the Player2
   process) for about 55 strategies of the form "hold vertical speed v, then switch to w", and every
   survivor must also have an escape for 12 more frames (three fallback strategies).
5. Scores survival first, then crystals, then distance to a resting height; presses the first key of the
   best plan. The fire shield is worth a lot because some pillars cannot be dodged without it.

Collision checks are the part that took the longest to get right:

* The engine's own pixel test builds temporary bitmaps and cost about 38 ms a plan. The bot uses its own:
  a sprite opacity mask per graphic, the ship's outline pixels looked up in the object's mask through the
  inverse rotation (integer maths, a small sine table; the device's FPU is not trusted for libm), a
  rotated-rectangle separating-axis prefilter, and a result cache. About 4 to 7 ms a plan.
* The ship's sprite changes with its vertical speed (graphs 77 to 85) and the tilted ones are taller, so
  each simulated step uses the silhouette of the sprite the script would show at that step.
* Validated against the engine's test (`SF3500_BOT_VALIDATE=1`): zero misses on fixed objects over
  788,000 samples; about 0.02% on rotating ones, which get a one-pixel tolerance because the engine
  rasterises one extra row or column at rotated edges.
* The bot never relies on the engine's collision test while playing; it is only used by the validation.

Difficulty (`bot_levels[]` in the file): Easy looks 18 frames ahead and replans every third frame with a 6%
slip rate; Normal 26 frames, every second frame, 2%; Hard 36 frames, every frame, no slips and a stronger
pull to crystals. A governor lengthens the replan interval if the moving average of planning time passes
12 ms. A `bot: perf` line is logged about every 250 frames and a `bot: RESULT` line each time its ship ends.

Results under emulation (2P Battle, Player 1 idle), completed levels out of 7:

| | shield available | shield taken by someone else |
|---|---|---|
| Hard | 1, 2, 4, 5, 7 | 1, 2, 4, 5, 6, 7 |
| Normal | 1, 2, 4, 5, 7 | 1, 2, 4, 5, 7 |
| Easy | none; lasts 5 to 20 seconds | |

Level 3 ends at a gauntlet of up and down pillars and obstacles about 870 frames in, in every setting.
`BOT_AVOID_RED=1` for `tools/bot-run.sh` makes the bot ignore the red crystal to reproduce "a human took the
shield first"; without that test the bot always had the crystal to itself, which hid a real failure.

Mistakes worth not repeating:

* Object slots are reused every tick and a new field (`ghost`) was not cleared, so real ground strips were
  treated as predicted pillars and the ceiling vanished from the plan. Clear a slot completely when filling it.
* The reference height for the mask tests was assigned before the ship's height was read, so every test was
  offset by last frame's movement.
* A check that the plan still has an escape must run on every surviving strategy, not on the best few by
  first-stage score; those are exactly the ones that ignore the escape.
* Weights must let a crystal outweigh a frame or two of slack, or the bot skips the shield.

## Device notes (SF3500)

* From a device log of the launcher and game: the launcher holds its 20 fps target, the game 25 fps, and
  audio underruns stayed at 3 to 4 over several minutes of play.
* The display driver drops frames larger than 640x480. The game's 320x240 is padded to 426x240 when
  *Original shape* is selected.
* Core dumps are not produced on the device. The runtime installs a crash handler that prints the faulting
  address and the memory map to the log.
* The device's clock reads 1970 (no RTC), so file times on the card are meaningless.

## Open

* The thruster (Alt) is not used by the computer opponent.
* Difficulty was tuned by feel under emulation; more play against it may suggest different settings.
